## Payment and work semantics

Checkout redirects never unlock purchases. Stripe payment state is fetched server-side. One-time purchases require a succeeded payment; fully refunded charges are rejected. Tracking is fulfilled by a paid subscription invoice, using its paid period, including the initial invoice. Repeated deliveries are deduplicated atomically by event ID and order/period. Monthly invoices queue future runs automatically; this also prevents a separate cron from accidentally running unpaid months. Cancellation stops new claims on canceled orders; paid-through dates prevent execution after expiry. Results already delivered remain available.

A worker claims one task atomically and records usage before a paid provider call. Interrupted tasks become failed, not automatically retried, because they might already have been billed. History excludes failures from percentages and displays coverage. Numerical comparisons require identical definitions/configuration and matching returned models. Actual search changes are disclosed. Monthly dates follow the subscription billing period, not a fixed 30-day timer.

Customer task usage is stored in `visibility_customer_usage.entry`, with original pricing version, actual model, tokens, searches and unknown costs. It is service-only; do not leak internal costs or another customer's usage into dashboard responses. The UI does not currently send completion emails; customers see saved results in their dashboard. Stripe receipts and account email delivery are configured separately.

## Complete package generation — November 19

Package version `complete-v2` replaces the short free-report completion adapter with a customer-only structured Responses request (10,000 output-token ceiling). It requires provider status `completed`, valid JSON, substantive homepage/service drafts, 3–6 evidence-backed priorities, and 4–6 FAQ answers. Truncated, refused, malformed or missing-section output is withheld and fails the task. Usage remains recorded even when output is rejected; there are no automatic paid retries.

Before generation, the worker reads the current homepage, discovers same-site homepage/sitemap links, and reads up to eight additional pages. Fetches reuse existing public-address, redirect and size protections. Service-like URLs are prioritized. This bounded snapshot is timestamped and retains unavailable URLs; it never claims to be a complete crawl. An unreadable homepage fails before a paid generation call. A service draft must target an actually read URL; it improves an existing page or homepage section rather than inventing duplicate service URLs. Older report observations remain dated separately from current page evidence.

Organization JSON-LD, the publishing checklist, and the measurement plan using the customer's exact saved questions are assembled by code, ensuring they cannot be omitted due to a long model draft. All eight sections are rendered into the existing dashboard/download format. Only customer worker/code changes are deployed; Hotline and the shared provider adapters remain unchanged. The owner review is a complimentary entitlement (no Stripe charge), explicitly labeled in job configuration.
